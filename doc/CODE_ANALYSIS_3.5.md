# 🔍 Аналіз коду EDwIC (версія 3.5.17)

Я провів детальний огляд кодової бази проекту. Проект має дуже солідну архітектуру (використання LittleFS, розумний логер подій у форматі NDJSON, профілі налаштувань, інтеграція з Telegram через FastBot2). Однак, знайдено ряд моментів, які потребують уваги для забезпечення стабільності при довготривалій роботі.

## ⚠️ Критичні помилки та логічні недоліки

1. **Переповнення таймера `millis()` (Timer Overflow)**
   У коді часто зустрічаються конструкції на кшталт `millis() > Alarm_data_milis` та `millis() < connecting_blink_end`. 
   *Чому це проблема:* Функція `millis()` переповнюється і скидається на 0 приблизно через 49 днів безперервної роботи. При такому порівнянні пристрій зависне або перестане виконувати заплановані дії після 49 днів аптайму.
   *Рішення:* Завжди використовувати безпечне віднімання: `millis() - start_time >= interval`.

2. **Безпека локального Web API (`WEB_serwer.ino`)**
   Роути `/api/` (наприклад, `/api/save`, `/api/reboot`, `/api/relay`) не мають жодної авторизації. Це означає, що будь-хто, хто підключений до тієї ж WiFi мережі (або до відкритої точки доступу ESP), може змінити налаштування, вимкнути пристрій або керувати реле без пароля.
   *Рішення:* Додати базову перевірку токена (наприклад, перевіряти заголовок `Authorization` або параметр `?token=...`), або хоча б дозволити керування тільки після автентифікації.

3. **Зависання пристрою у `PowerMonitor.ino`**
   Після спрацювання переривання живлення, код входить у `while (true) { yield(); }`, чекаючи на повне розрядження іоністора. Якщо в цей час живлення 220В раптом відновиться (короткочасний збій на 1-2 секунди), пристрій залишиться "завислим" до спрацювання Watchdog, замість того, щоб відновити роботу.
   *Рішення:* Потрібно додати перевірку в циклі: якщо живлення відновилося, робити `ESP.restart()` або безпечно повертатись до роботи.

4. **Блокуюче підключення до WiFi (`WiFi.ino`)**
   Функція `WiFi_Conect()` містить блокуючий цикл `while (WiFi.status() == WL_DISCONNECTED && y < 40) { delay(100); }`. Це зупиняє головний цикл `loop()` на 4 секунди. У цей час не працюють переривання таймерів для Web-сервера чи Telegram. 
   *Рішення:* Реалізувати кінцевий автомат (State Machine) для підключення у фоновому режимі (неблокуюче).

## 💡 Оптимізація коду та пам'яті (RAM)

1. **Оптимізація стрімінгу JSON (`WEB_serwer.ino`)**
   Зараз для генерації відповідей використовується:
   `String out; serializeJson(doc, out); _sendJson(200, out);`
   Для великих JSON-документів (наприклад, `/api/config`) це створює великий цільний об'єкт `String` у пам'яті, що призводить до сильної фрагментації купи (Heap fragmentation). 
   *Рішення:* Використовувати прямий стрімінг у клієнта: `serializeJson(doc, WebServer);`.

2. **Використання пам'яті у Logger (`AA_Logger.ino`)**
   Зараз логер використовує 6 паралельних масивів замість структури (для уникнення конфліктів компілятора Arduino). Це забирає близько 1.3 КБ RAM статично. Хоча для ESP8266 це прийнятно, перехід на `struct LogEntry` (який вже задекларовано в `set.h`) та масив структур зробив би код набагато чистішим.

## 📁 Порядок у файлах (Структура проекту)

1. **Дублювання `set.h`**
   У проекті існує два файли `set.h`: один в корені проекту, інший в папці `src/`. Використовується той, що в `src/`. Кореневий файл є застарілим і створює плутанину. Його слід видалити.

2. **Архітектура `.ino` файлів**
   Проект розділений на 15+ `.ino` файлів. В екосистемі Arduino це працює, оскільки середовище склеює їх в один великий файл перед компіляцією. Однак для PlatformIO це погана практика, оскільки це ускладнює контроль області видимості змінних (Scope) та уповільнює компіляцію. 
   *Пропозиція:* Якщо планується подальший розвиток, варто провести рефакторинг — перейменувати всі `.ino` на `.cpp` і створити відповідні заголовні `.h` файли з деклараціями (або один загальний `globals.h`).
